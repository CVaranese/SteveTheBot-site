Project+ in Dolphin

12 Nov 2026 · T-5, T-23 · Project+

Abstract

About 600 to 720 frames a second for one copy; a Melee model plays whole P+ games.

A Melee-trained model plays whole P+ games through a translator. A savestate bug in the scripting Dolphin ran P+ at double speed and dropped every second input; our fork fixes it.

Question and hypothesis

The project's target game is Project+, a mod of Super Smash Bros. Brawl, which has no fast simulator; it runs only in the Dolphin emulator. Three things had to be known before any work on it: how fast the game runs in an emulator that a script can drive, whether a script's inputs reach the game reliably, and whether a model trained in Melee can play Project+ at all when the game state is translated for it.

Written in the experiment plan on 12 Nov 2026, before the runs:

Run 1 (default video, speed 0, neutral inputs, 3,600 frameadvances): 150 to 500 frameadvances/s

Run 2 (as run 1, random inputs on both ports): within 20% of run 1.

Run 3 (as run 2 with -v Null): either refuses / ignores it, or 1.2 to 2 times run 2.

A: about half of the frames show a new value (every 2nd value is lost); the lag is one fixed number all run.

C: the same half-rate, but the lag or the parity shifts during the run in at least one copy.

"Frameadvances" are emulator frames stepped by the script. The first three quotes are about speed. The last two are about the input probe: run A is one copy of the emulator, run C four copies at once. No expectation was written down for the fix or for the games played by a Melee model.

Setup

Four parts, all on 12 Nov 2026: timing runs with one copy of the emulator; the input probe with one and with four copies; the same probe after a fix to the emulator; and games in which a Melee-trained model plays Project+. The fix was made in a fork of the scriptable emulator build, which is a separate code base and not in the project's code repository.

Discussion

The game runs many times faster than real time in one copy. Table 2 gives the game frames per second of three whole runs; real time is 60. The first quote guessed a much lower speed. Turning the video output off gained little, less than the third quote's lower bound.

Before the fix, only every second scripted input reached the game. In Table 3 a new code is seen on half of the frames, and every code seen is two or three frames old. The pattern is the same with four copies at once: the fifth quote expected it to shift under load, and it did not.

Before the fix the game was also running at twice its normal rate. At normal speed the unfixed emulator stepped about twice as many frames per second as the fixed one (the two lines after Table 5).

With the fix every input lands. In Table 4 every code seen is one or two frames old, and Table 5 shows no step larger than one between successive codes, so no input was skipped, in one copy and in four at once.

A Melee-trained model plays whole games of Project+. With the model on both sides, one game ran to its end, and the helper found an exact Melee counterpart for most of the decisions in it (the play lines above). Against an opponent that stands still the exact share was higher.

Limitations

  • The speeds in Tables 2 and 3 were measured before the fix, while the game ran at twice its normal rate; the speeds with the fix (Table 4) come from short probe runs that include start-up.
  • Whole-run speeds in Table 2 include the end of a match; speeds inside a match were somewhat higher and are not shown.
  • One of the four copies did not start in the unfixed four-copy run. Start-up hangs were looked at separately and are not shown here.
  • The fix lives in a fork of the emulator outside the project's code repository; its source is not cited here.
  • The games played by the Melee model were not recorded, and how well it played was not measured; the page shows only that games complete and how much of the state maps.
  • One character on both sides, one stage.

Decision

Falcon against Falcon on Battlefield or Final Destination; no Melee level is required first.
