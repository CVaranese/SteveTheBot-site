A Captain Falcon that learns Melee, on the way to Project+

A reinforcement-learning bot from 2017, revived and retrained on a fast Melee simulator. This page has three parts: the roadmap (what each part of the system is now and what comes next), progress (every improvement scored against the same opponents), and how the trainer works.

The controller

timing changedheads not default
Now · changed 12 NovOne of 54 fixed actions: 9 stick positions times one button or none. New PPO models (sim/ppo_run.py) now choose an action every frame, and each action reaches the controller 11 frames (0.19 s) later, like a human reaction time. Models trained before this, and the old 2017 learner, choose every 2 frames with no delay.
Cost, measured in T-16 with a delay of 15 (not 11): far weaker than no delay (level 9 in-game CPU in Dolphin, 10 of 50 wins vs 42 to 46). So this default trades current strength for human-like timing. A model trained with 11 frames at the new default has not been scored against the in-game CPU yet.
Built and tested 12 Nov
  • Each saved model has a small settings file: frames per action and delay. Missing means every 2 frames, no delay.
  • --frames-per-action 1 --delay D: a decision every frame. An action chosen on frame t reaches the controller on frame t+D, a human-like reaction time. Tested with D = 15 (Firoiu et al. 2018). The default for new PPO models is now D = 11.
  • With a delay the network also sees the D actions still in flight, as 54-slot one-hots: at D = 11, 796 + 11 x 54 = 1,390 inputs (at D = 15 it was 1,606).
  • Discount and GAE decay are scaled to the shorter step, so one update covers the same game time.
  • Self-play delays both sides. The scripted opponent is not delayed (it stands in for the in-game CPU).
Trained and tested, 2,940 updates, two seeds each. Wins vs level 9 scripted bot / frozen T21L6Cs4 (of 100) / level 9 in-game CPU in Dolphin (of 50): every 2 frames 84 and 94 / 27 and 9 / 42; every frame, no delay 94 and 87 / 11 and 7 / 46; every frame + delay 15: 1 and 2 / 0 and 0 / 10. A delay of 15 is far weaker against opponents that have no delay. Your decision: every frame with a 0.19 s delay, 11 frames (--delay 11), used for the two-head tests below and, since the last change, the default of ppo_run.py for new models. Resumed models keep their own settings; --frames-per-action 2 --delay 0 gives the old behaviour.

One score per skill: the scenario yardstick (T-28)

Whole-game wins mix every skill together and swing a lot between runs. The simulator can save a whole match and load it again exactly. So moments are saved from earlier games (an opponent knocked off the stage; the frame a first hit lands). Every model is then put into the same 300 saved positions and plays on. The result is one score per skill. The saved positions come from our own bots' games, not human games. This is version 2; the table below replaces version 1.

What version 1 got wrong. Edgeguard and recovery were judged inside a time limit, and many starts were already lost before play began (the offstage player could not get back even with no one guarding). That made edgeguard look like 21% to 28%. Version 2 judges by outcome with no time limit: the offstage player gets back on the stage and can act, or loses the stock. Starts that were already lost are removed first: each offstage start is replayed with the best model recovering and nobody guarding. The critic's value guess was tried as the filter, but it matched the replays only weakly (correlation 0.59), so the replays are used. Three neutral tests were added.

A second fault, found after watching. The user spotted an edgeguard sample that ended oddly. A check showed many starts were already safe, not only already lost: of 321 kept starts, 84 got back on the stage with no input at all, and 67 more were back in under a second with nobody guarding. The filter now keeps a start only if the best model can get back unopposed, has to act to do it, and needs at least a second. That leaves 170 of 380 starts.

Part 3

How the trainer works

Each block explains one idea in the current trainer (sim/ppo_run.py), with this project's own numbers.

One update, start to finish

  1. Play64 matches run at once. The actor picks an action for each player: every frame at the new default, 256 decisions per match (every 2 frames: 128). Same game time either way.16,384 per side (8,192 at 2 frames)
  2. ScoreEach decision gets its reward, and the critic guesses the value of every state.reward: stocks, damage
  3. JudgeGAE turns rewards and guesses into an advantage: how much better each action went than expected.λ 0.95, discount 0.995 per 2 frames (scaled for every frame)
  4. Learn4 passes over the batch in 4 slices. Actor and critic both take small gradient steps.16 steps, lr 6e-4
play the matches 87%learn 13%

One update takes about half a second for a run alone on the GPU. A full run is 2,940 updates, about 3,800 to 4,900 games. Self-play learns from both players' views, since both are the same network.

Two networks: one acts, one judges

The actor reads the state and gives a probability for each of the 54 actions. The bot samples one, so it does not always do the same thing in the same spot. The critic reads the same state and guesses how much reward is coming. They share no weights.

768 of the 796 inputs say which animation each player is in, one slot per animation. So the first layer is mostly a lookup table from animation to 128 features, which is why it holds 81% of the weights. New models use plain inputs. An optional embedding can go in front (--embed 32 --embed-std 0.05; it was the default for a few hours on 12 Nov and was dropped, see the progress table): each 384-slot block becomes 32 learned numbers from one table shared by both players, so the first layer sees 92 numbers and the weight counts above shrink (the layer sizes drawn here are the models without it; counts recomputed from Model.py). The other front layers stay optional: rescaling shrinks x, y and hitstun (which spread up to 6 times wider than the other inputs) so no input drowns out the rest. Both are stored inside the saved model, so older models load unchanged.

The advantage, and how GAE estimates it

Learning needs to know whether an action was good. The raw reward is too noisy (a stock is lost seconds after the mistake), so the trainer asks: did things go better or worse than the critic expected? That difference is the advantage A. A positive A makes the action more likely next time, a negative one less likely.

δt = rt + γ·V(st+1) − V(st) · At = δt + (γλ)·δt+1 + (γλ)²·δt+2 + …

δ is a one-step surprise: the reward plus the critic's new guess, minus its old guess. GAE adds up the surprises that follow, each weighted less. λ sets the trade: near 0 trusts the critic (low noise, but biased when the critic is wrong), near 1 trusts the real rewards (unbiased, noisy). The discount γ says how much future reward counts at all.

The PPO clip: learn a lot from each batch, but not too far

The 2017 learner used each batch once and threw it away. PPO goes over the same batch 4 times. That is only safe if the policy cannot drift far from the one that played the games, so PPO compares the new and old probability of each action (the ratio r) and stops rewarding changes past a band of ±ε.

r = πnew(a) / πold(a) · actor loss = −min(r·A, clip(r, 1−ε, 1+ε)·A) − 0.01·entropy

The learning rate, and how to tell it is too small

The learning rate is the size of each weight change. Too large and training swings or collapses; too small and the network barely moves. The usual check is approx_kl: how far one update moved the policy, measured as a divergence between the old and new action probabilities. PPO runs commonly sit near 0.01.

The old default moved the policy about ten times less than usual, and lowering the rate to zero meant the second half of each run learned almost nothing. Two settings with the same total step size over the run (3e-4 constant and 6e-4 falling to zero) ended about equal; doubling the total won 97 of 100. Doubling again (1.2e-3) did not help: the policy narrowed fast (one run's entropy fell to 1.95) and scored worse. That is the other side of the trade: steps too large lock in early habits. So 6e-4 stays. Longer runs were the next lever, and they work: at 5,880 updates every model beat its own 2,940-update checkpoint, 93 to 100 games of 100, and the runs were still learning at the end. The last column of this table is the first T-21 runs only.

Entropy: how random the bot still is

Entropy measures how spread out the action choice is. Picking uniformly among 54 actions gives 3.99; always picking one action gives 0. The trainer adds a small bonus for entropy (0.01) so the bot keeps trying things instead of settling early. The 2017 learner stayed at 3.93, close to random. The first PPO models ended near 3.3, and the new default ends at 2.7 to 2.8, the lowest so far. The game report found that much of the remaining randomness is harmless: in 57% to 70% of decisions the character is mid-move and no input could change anything.

Self-play, frozen opponents and seeds

  • Self-play: the same network plays both sides, so its opponent improves with it. The risk is learning to beat only itself, which is why scores also use other opponents.
  • Frozen opponent: a saved model that no longer learns. It is a fixed bar to measure against. When everything beats it, a stronger one is frozen (this happened today).
  • Seeds: the same training repeated with different luck. Identical settings have ended 10 to 13 wins apart on an easy opponent and up to 30 apart on the hardest, so each setting gets at least two runs, and plain runs in the same batch, before a decision.
  • Rule for a new default: fixed before the runs, so results cannot bend it. The one in use (mean of at least 60 against frozen PPO8Self) has stopped working, because that opponent is now too easy. Approved 12 Nov: against frozen T21L6Cs4, a change must beat plain runs from the same batch by at least 10 wins on average, with no run below the lowest plain run.
